# Работа с Document Insight System

Инструкции действуют для всего репозитория. Сверяй документацию с текущим кодом:
[README.md](README.md) описывает запуск и API, [docs/criteria.md](docs/criteria.md) —
критерии, [CHANGELOG.md](CHANGELOG.md) — изменения поведения и миграцию.

## Границы изменений

- Перед правкой проверь `git status` и diff затрагиваемых файлов. Сохраняй чужие
  незакоммиченные и staged-изменения; не выполняй reset, checkout или массовое форматирование.
- Делай изменения в рамках задачи. Push, PR, теги, релизы и публикация образов требуют
  прямого запроса пользователя. Сборка сама по себе не означает разрешение на публикацию.
- Перезапуск сервисов, миграция существующих данных и сквозной тест действующей БД
  должны входить в запрошенную задачу. Для обычной правки документации они не нужны.
- Не выводи секреты из `.env`, cookie, токены и содержимое пользовательских документов.
  Для примеров используй placeholders; `.env` не должен попадать в Git.
- Не правь файлы в `files`, данные MongoDB и результаты проверок как тестовые фикстуры.
  Пользовательские вспомогательные скрипты вне задачи оставляй без изменений.

## Карта кода и окружение

- Python 3.12; frontend собирается на Node.js 20. Правила Python — в `ruff.toml`.
- `app/main/parser.py` выбирает разборщик; `app/main/reports` работает с DOCX/MD/PDF,
  `app/main/presentations` — с PPTX, `app/nlp` — с текстом.
- `app/main/checks` содержит реестр критериев, `app/main/check_packs` — инициализацию
  и оценку. `app/tasks.py` связывает конвертацию, Celery и сохранение результата.
- HTTP-контракт находится в `app/routes`, миграции БД — в `db_versioning`.
- Существуют импорты `app.*` и старые импорты из корня `app`. Для локальных проверок
  используй `PYTHONPATH=app:.`; в Docker нужны оба абсолютных пути проекта и `app`.
- Полная обработка требует LibreOffice, системных библиотек md2pdf, MongoDB и Redis.
  Для проверки внешних границ используй Docker; импорт модуля не доказывает работоспособность конвертации.

## Frontend и интерфейс

- Исходники JavaScript/CSS находятся в `assets`, HTML — в `app/templates`.
  Точки входа перечислены в `webpack.config.js`. Каталог `src/` — сгенерированный
  результат Webpack, который Flask отдаёт как static; не исправляй bundles вручную.
- После изменения assets запускай `npm run build`; для локальной разработки есть
  `npm run watch`. Монтирование `app` в dev Compose само по себе не пересобирает assets.
- При изменении формы или ответа HTTP сверяй обработчик Flask и вызывающий его JS.
  Для пользовательских текстов сохраняй русский язык и принятую терминологию.

## MongoDB и миграции

- Подключение приложения и GridFS — в `app/db/methods/client.py`, модели — в
  `app/db/types`, операции с коллекциями — в `app/db/methods`.
  Сейчас используются адрес `mongodb://mongodb:27017` и БД `dis-db`;
  не предполагай, что произвольный `MONGO_URL` в `.env` меняет это подключение.
- Версия схемы независима от версии приложения. При изменении структуры данных
  проверь `db_versioning/versions.py`: классы версий, `VERSIONS` и `LAST_VERSION`.
  Сохраняй существующие миграции; новый переход должен явно учитывать исходную версию.
- Текущий runner вызывает миграцию последней версии для текущего состояния БД,
  а не последовательно все промежуточные. Не рассчитывай на автоматический переход
  через несколько версий; старое переименование БД также требовало ручного шага.
- `scripts/local_start.sh` запускает миграцию перед web и останавливается при ошибке.
  Проверяй миграции на отдельной БД/копии, не на пользовательских данных.
  Сохраняй связь исходника, результата и PDF в GridFS и их разные идентификаторы.
- Инициализация создаёт администратора при отсутствии учётной записи; изменение
  `ADMIN_PASSWORD` в окружении не обновляет пароль существующего пользователя.

## Фоновые задачи

- Конвертация и проверка используют очереди `convert-pdf` и `check-solution`.
  При изменении task routing сверяй `app/tasks.py` и `CELERY_QUERIES` в Compose.
- LTI passback использует отдельную очередь `passback-grade`. Beat планирует задачу,
  но стандартный список очередей worker её не потребляет. Наличие расписания
  не доказывает доставку оценки в LMS.
- Сохраняй корректность при повторной доставке/retry и порядок сохранения результата
  и удаления временных файлов. Не удаляй исходник или PDF, нужный следующему шагу/retry.
  Статус Celery, окончание проверки и проходной балл — разные состояния.
- При старте worker обработчик `worker_ready` сейчас скачивает NLTK `stopwords` и
  `punkt`. Проверки текста имеют резервные пути, но запуск worker нельзя считать
  полностью автономным от сети только по отсутствию загрузок внутри критериев.

## Версия и зависимости

- Меняй версию приложения только в `package.json.version` (`MAJOR.MINOR.PATCH`).
  Выполни `make sync-version` и `make check-version`. Сохраняй изменения манифеста
  вместе с `package-lock.json`; не добавляй номера версии в Dockerfile или `.env_example`.
- Make передаёт версию, commit, дату, ветку и состояние исходников в образы.
  `app/build_info.py` читает окружение образа или локальный манифест.
  Не возвращай промежуточные `VERSION.json`, example-файлы и генераторы метаданных.
- Изменение номера приложения не должно обновлять дерево зависимостей.
  Синхронизация версии затрагивает только поля версии npm lock и локальный `IMAGE_VERSION`.
- npm устанавливается через `npm ci`. Python устанавливается из `requirements.lock`
  с `--require-hashes`. При изменении `requirements.txt` обновляй lock через pip-tools
  в отдельном окружении Linux/Python 3.12; точная команда есть в README.
- Не подменяй lock установкой незакреплённых пакетов в Docker. Ruff — инструмент
  разработки, его отдельная установка не требует добавления в runtime-зависимости.

## Изменение критериев

- ID уникален вместе с типом `report`/`pres`, а не во всём приложении.
  Реестр `AVAILABLE_CHECKS` собирается динамически; классы вспомогательных модулей
  не должны случайно становиться отдельными критериями.
- Конструктор получает служебный `file_info`; пользовательские параметры приходят
  из `["id", {…}]`. Сохраняй совместимость существующих наборов или явно описывай миграцию.
- Результат `check()` содержит `score` и `verdict`. Рекомендации исключаются из среднего;
  ноль обязательного критерия обнуляет набор. `priority`/`warning` — свойства реализации,
  их нельзя считать универсальными пользовательскими параметрами конструктора.
- Неизвестный ID и ошибка инициализации должны оставаться видимыми ошибками настройки.
  Эквивалентные записи дедуплицируются, разные параметры одного ID сохраняются.
- Проверяй пустой ввод, отсутствие раздела, граничные значения, повторный вызов,
  вложенность и независимость от порядка критериев. Не мутируй общие карты конфигурации.
- Различай DOCX и MD: MD не имеет геометрии и стилей Word. PDF-страницы нумеруются
  от 1; границы диапазонов включительные. Не добавляй искусственный минимум страниц MD.
- Не загружай NLTK-корпуса во время обработки. Сетевые проверки должны иметь timeout
  и понятное сообщение при недоступности внешнего сервиса.
- При изменении параметров, алгоритма или оценки обнови `docs/criteria.md`, базовые
  наборы при необходимости и раздел изменений в CHANGELOG. Не описывай эвристику
  как семантическую проверку качества работы.

## Совместимость HTTP API

Внешние системы используют `POST /tasks/md` без cookie, с `access_token` в multipart-форме.
Сохраняй строковый `check_id` по умолчанию и JSON `task_id`/`check_id` при непустом
`full_response`. Строка `"false"` тоже непустая. Не заменяй контракт обязательным
Bearer-токеном, сессией или новым форматом ответа без отдельной задачи на миграцию клиентов.

Различай `check_id`, Celery `task_id` и `conv_pdf_fs_id`. Готовность не означает успешную
обработку. Токен загрузки не даёт доступ к HTML/PDF/журналам вместо сессии; экспорт
CSV/ZIP принимает токен в query. Не расширяй доступ к данным попутно с исправлением API.

## Контейнеры и существующие данные

Web, worker и Flower работают как `app` (`10001:10001`) с `cap_drop: ALL`.
Только `volumes-init` получает root и ограниченные capabilities для подготовки
`files`/`flower_data`; он работает без сети, не разыменовывает симлинки и не меняет содержимое файлов.

Не решай ошибки доступа запуском приложения от root или `chmod 777`.
При миграции сначала останови старых писателей, затем подготовь существующие volume
и пересоздай сервисы. Не используй `down -v` и не меняй имя Compose-проекта для миграции.
`restart` не применяет новый образ или `USER`. Домашний каталог app нужен для записи,
исходники остаются во владении root.

`make build-all` последовательно собирает worker-base и приложения. `make build`
может использовать готовую базу, поэтому после её изменения нужен `build-all`.
Worker не читает `.env` целиком: новые настройки явно передавай в его `environment`.
Проверяй совпадения имён с настройками сторонних программ: проектный `FLOWER_AUTH`
передаётся в Flower как `FLOWER_BASIC_AUTH`, иначе Flower воспринимает его как настройку OAuth.

## Проверка результата

Выбирай проверки по затронутому поведению. Для исправлений критериев/разборщиков
добавляй регрессионный сценарий, воспроизводящий проблему, и запускай:

```bash
PYTHONPATH=app:. .venv/bin/pytest -p no:cacheprovider -c /dev/null --rootdir=. --import-mode=importlib -q tests/criteria tests/reports
.venv/bin/ruff check app/main/checks app/main/check_packs app/main/reports app/main/presentations app/nlp tests/criteria tests/reports tests/util
```

Для синхронизации версии: `python3 scripts/test_versioning.py` и `make check-version`.
Для frontend: `npm ci` и `npm run build`. Для документации проверь ID, параметры,
команды и относительные ссылки; полный Docker-пайплайн без изменения поведения не нужен.
Заверши проверкой `git diff --check`.

Не запускай весь каталог `tests` обычным pytest вместо указанной команды:
рядом находятся Selenium-сценарии и отдельный `tests/reports/pytest.ini`.
`make tests` запускает UI-окружение в фоне и не подтверждает успех тестов.
При добавлении фикстур проверь `git status --short --untracked-files=all` и
`git check-ignore`: глобальные правила игнорируют, например, DOCX/PDF/PPTX и Markdown.
Нужные тестовые файлы должны быть доступны после чистого клонирования.

CI форматирования выполняет `ruff format --check .` и `ruff check .` для всего
репозитория. Успех выборочного Ruff не означает успех полного CI. Если полная
проверка обнаружила проблемы вне задачи, сообщи об этом отдельно; не запускай
массовое автоисправление чужого кода.

Тесты критериев подменяют внешние сервисы. Для задачи на развёртывание после сборки
и запуска используй `scripts/verify_deployment.py` по команде из README: он обращается
к реальным сервисам и **создаёт три проверки в текущей БД**. Отдельно проверяй UID/GID,
доступ к старым файлам и их сохранность. Не объявляй LTI passback проверенным по этому сценарию.

В отчёте укажи сделанные изменения, выполненные проверки и оставшиеся ограничения.
Различай реально выполненный сквозной тест, тесты с подменами и проверку конфигурации.

## Финализация и Git

- Перед коммитом отделяй изменения задачи от локальных скриптов и материалов ревью.
  Добавляй файлы явным списком; не используй `git add .` в грязном каталоге.
- Перед push обнови сведения об удалённой ветке. Не используй force push.
  Не включай посторонние ветки без проверки их diff и истории.
- Для удаления кода проверяй импорты, вызовы, шаблоны, Webpack и динамический реестр.
  Отсутствие прямого импорта не доказывает, что критерий не используется.
- Не удаляй регрессионные тесты только потому, что ошибка уже исправлена.
- Сквозные проверки запускай на отдельном Compose-проекте с отдельным MongoDB volume
  и портами. Одно имя проекта не изолирует bind mount MongoDB.
- Сохраняй итог проверки в документации: коммит, команды, результат и ограничения.
  Не называй релиз проверенным, если сборка или реальный API не были проверены.
