# Роадмап Document Insight System

Рабочий план от 2026-10-16. Основан на состоянии кода после подготовки 3.0.0 и
предрелизной проверки. Приоритеты: надёжность и качество проверок,
удобство преподавателей/студентов, новые проверки и интеграции.


## Последовательность

| Этап | Основной результат | Надёжность и качество | Удобство | Интеграции |
|---|---|---|---|---|
| Подготовка 3.0.0 | Зафиксированная отправная точка | Закрыть результаты аудита, проверить состав коммита | Актуальные инструкции и миграция | Сохранён старый API |
| 3.0.1 | Устранение известных сбоев | Валидация, завершение ошибочных задач, воспроизводимый запуск | Понятные ошибки вместо зависания | Контрактные тесты существующих клиентов |
| 3.1.0 | Управляемая проверка документов | Эталонный корпус, история настроек и измерение качества | Первая версия редактора наборов и удобный результат | Минимальный версионированный API |

Каждая версия должна приносить завершённый пользовательский сценарий.

## Перед началом новых возможностей

- Проверить, что исправления предрелизного аудита, включая тестовые фикстуры и запуск Flower,
  вошли в выбранный коммит. Прогонять проверки на чистой копии именно этого состояния.
- Зафиксировать исходные показатели: время ожидания, конвертации и проверки, число
  технических сбоев, расход памяти на типовых документах. Разделять DOCX, MD и PPTX.
- Выбрать владельца приоритетов и 2–3 пользователей для проверки интерфейса: преподавателя,
  студента и, по возможности, владельца внешней интеграции.
- Собрать небольшой набор обезличенных работ с ожидаемыми нарушениями. Реальные
  студенческие документы и секреты не включать в публичный репозиторий.

## 3.0.1 — стабилизация

Патч содержит совместимые исправления. Новые публичные возможности, формат результата
и изменение правил выставления балла относятся к следующей minor-версии.

| ID | Задача и основание | Условие готовности |
|---|---|---|
| R01 | Проверять загрузку до обращения к имени файла. Сейчас оба обработчика в [tasks.py](../app/routes/tasks.py) читают `file.filename` раньше проверки наличия файла; имя без расширения также требует обработки. Проверять выбранный набор до постановки задачи. | Для отсутствующего/пустого файла, имени без расширения, неверного MIME и неизвестного набора есть регрессионные сценарии; нет необработанного 500 и лишних файлов/записей задачи. |
| R02 | Обрабатывать некорректный и неизвестный `check_id`, ошибки конвертации и исчерпание retry. Опрос готовности не должен оставаться единственным способом понять сбой. | Контролируемая ошибка конвертации и падение обработки дают конечное состояние с причиной; клиент и пользователь не ждут бесконечно. Проверены отказ Redis/worker и повторная доставка. |
| R03 | Перевести рабочий запуск с Flask development server/reloader на production WSGI-сервер. Сейчас `-p` всё ещё приводит к `app.run(..., use_reloader=True)` в [server.py](../app/server.py). Сохранить инициализацию администратора, LTI и порядок миграций. | Запуск и штатная остановка проходят без reloader; web/API, миграции, admin и LTI-инициализация работают. Новая зависимость закреплена в lock. |
| R04 | Убрать обязательное скачивание NLTK при старте, явно настроить concurrency/память и timeouts обработки. | После загрузки образов запуск и проверка тестового корпуса не требуют скачивания NLTK; на выбранной конфигурации нет OOM. Число процессов задаётся настройкой, а не случайным числом CPU хоста. |
| R05 | Проверить резервное копирование восстановлением MongoDB/GridFS и файловых данных в отдельное окружение. Само наличие `backup_db.sh` не подтверждает восстановление. | Есть инструкция и воспроизводимый restore-тест: старый результат, исходник и PDF доступны после восстановления. Записаны измеренные время и объём копии. |
| R06 | Зафиксировать контракт старого API тестами: multipart-токен, строковый/JSON-ответ, опрос готовности, SVG и экспорт. | Тесты выполняются в CI; прежние клиенты продолжают работать без изменения своих запросов. Для новых обработанных ошибок явно описано поведение. |

Минимум версии: R01, R02, R06 и проверенная инструкция восстановления R05.
R03/R04 включать только с полноценной проверкой запуска; если они задерживают исправления
API, выпустить отдельный совместимый патч 3.0.2. Не объединять срочный фикс с большой
перестройкой приложения.

Отдельный приоритет до новых возможностей — доступ к документам. В текущем
[get_pdf.py](../app/routes/get_pdf.py) есть `login_required`, но в самом обработчике
нет проверки владельца конкретного файла. Проверить весь путь чтения и матрицу доступа
«владелец / другой пользователь / администратор / LTI / API», затем закрыть доступ
к чужим приватным документам с регрессионными тестами. Явные публичные сценарии
и совместимость API при этом должны быть сохранены; изменения доступа описаны.
Наличие авторизации само по себе не заменяет проверку доступа к конкретному объекту.

## 3.1.0 — качество, настройка и API

### Качество проверок и воспроизводимость

| ID | Задача | Условие готовности |
|---|---|---|
| R07 | Создать эталонный корпус DOCX/MD/PPTX с разметкой ожидаемых нарушений. Начать с 15–20 небольших случаев: правильный документ, отсутствие разделов, подписи/ссылки, списки, вложенность и оформление. Отдельно собрать реальные обезличенные работы для ручной оценки. | Для каждого случая известно ожидаемое поведение и почему оно верно. Публикуемые фикстуры синтетические; права и порядок доступа к реальным примерам согласованы. |
| R08 | Измерять ложные срабатывания и пропущенные нарушения по критериям, а не только долю прошедших unit-тестов. В первую очередь — тема, цель/задачи, «вода», аббревиатуры и подписи. | Есть исходная таблица ошибок и сравнение до/после. Изменения порогов проверяются на отложенных примерах; отдельно учитывается «неприменимо к формату». |
| R09 | Сохранять снимок параметров набора, его ревизию, версию приложения/исходников и хеш исходного файла при проверке. Повторную проверку хранить как отдельную попытку. | Изменение набора не меняет смысл старого результата; видно, каким набором и версией он получен. Старые записи читаются с явно неизвестной ревизией. Для точного повторения также фиксируются существенные версии конвертеров/внешних сервисов. |

Не вводить новые веса критериев и не менять формулу итогового балла одновременно
с калибровкой порогов: иначе невозможно понять причину изменения оценки.

### Интерфейс преподавателя и студента

| ID | Задача | Условие готовности |
|---|---|---|
| R10 | Сделать первую версию редактора наборов поверх реестра: выбор критериев, допустимых форматов и параметров. JSON оставить как дополнительный режим импорта/экспорта. | Преподаватель создаёт и проверяет небольшой набор без ручного JSON; неизвестные параметры и неприменимые к MD проверки объясняются до сохранения. Сохранённый набор проходит round-trip без изменения значений. |
| R11 | Разделить в интерфейсе оценку работы, техническую ошибку и рекомендацию. Показывать этап обработки, время начала/окончания, причину сбоя и действие пользователя. Для замечания — правило, найденное нарушение и переход к PDF, если координата известна. | Пользователь отличает плохую работу от сбоя конвертации и предупреждения LanguageTool. На 2–3 пользовательских сценариях замечание находится и объясняется без чтения серверного журнала. |

Для редактора сначала подготовить схему параметров с типами, границами и совместимостью

все ограничения и зависимые настройки. Из этой же схемы можно постепенно получать
валидацию и части справочника.

## 3.2.0 — массовая работа и интеграции

| ID | Задача | Условие готовности |
|---|---|---|
| R13 | Подтвердить LTI-пайплайн целиком, включая очередь `passback-grade`, повторную доставку, недоступность LMS и защиту от отправки устаревшей оценки. Стандартный список очередей сейчас не включает passback. | В тестовой LMS/совместимом стенде загрузка завершается возвратом ожидаемой оценки; после сбоя доставка восстанавливается без неверного обновления. Администратор видит статус и причину отказа. |
| R14 | Добавить отдельные учётные данные внешних клиентов: область доступа, отзыв/ротацию и аудит обращений. Идемпотентность загрузки — для нового API. | Клиент видит только разрешённые ему результаты; повтор запроса с одним ключом не создаёт лишнюю проверку. Старый общий `access_token` остаётся поддерживаемым режимом до отдельно согласованной миграции. |
| R15 | Пакетная загрузка и управляемая перепроверка, фильтры по набору/статусу, сравнение попыток и экспорт выбранных результатов. Начать с ограниченной очереди файлов; ZIP-вход требует отдельной проверки безопасной распаковки и лимитов. | Преподаватель обрабатывает согласованный тестовый пакет без ручной загрузки каждого файла; повторные запросы не дублируют работу, ошибки отдельных файлов не теряются, видна история оценок. |
| R16 | Показатели эксплуатации: длительность этапов, возраст очереди, технические сбои, ошибки критериев и конвертации. Readiness web/worker и проверка восстановления после рестарта. | Можно найти зависшую проверку по ID, отличить нехватку worker от ошибки документа и увидеть деградацию на графике. Уведомления имеют измеренный порог; содержимое работ и токены не попадают в метрики. |

Зависимости: R09 нужен для корректного сравнения попыток; R12 и модель доступа — для R14;

повышается, если возврат оценки в LMS уже используется в рабочем процессе.
В таком случае проверку потребителя `passback-grade` и базовую доставку оценки
выполнить уже в ближайшем патче; обработку отказов и расширенную диагностику
R13 развивать дальше, не откладывая восстановление существующей интеграции до 3.2.

## Что изучить после этих версий

- **Общая модель документа.** Постепенно выделять заголовки, абзацы, списки, таблицы,
  рисунки и ссылки в общий контракт. Сначала один критерий и регрессионные примеры,
  затем следующие; избежать одновременного переписывания всех 63 критериев.
- **Детальные ссылки на нарушения.** Координаты и выделение фрагментов PDF там, где
  сопоставление с исходником надёжно. Не выдавать предполагаемую страницу за точную.
- **Картинки и таблицы.** Изучить привязку реальных объектов к подписям: текущая проверка
  не гарантирует соответствие каждому объекту. Сначала сформулировать правила для
  нескольких изображений под общей подписью и сложных таблиц.
- **Модернизация зависимостей.** Небольшими совместимыми группами после построения
  корпуса и интеграционных тестов. Не обновлять Flask, MongoDB-клиент, конвертацию
  и весь frontend одним изменением.
- **Webhook и LTI 1.3.** Добавлять по запросу конкретного потребителя, с проверкой
  подписи, повторов и отказов. Webhook требует заранее готовых событий и модели доступа.
- **OCR и новые форматы.** Начать с исследования реального спроса, эталонных сканов,
  качества распознавания и стоимости обработки. Самостоятельный PDF — отдельный
  тип входа с ограниченным набором проверок, не замена DOCX для проверки стилей.
- **ИИ-проверки содержания.** Только как экспериментальные рекомендации: размеченный
  корпус, объяснимый результат, правила обработки данных и измерение ошибок. Не включать
  их в обязательную оценку без отдельной проверки и согласования.

## Условия выпуска каждой версии

- Выбран конкретный коммит; тесты, сборки и фикстуры воспроизводятся из чистой копии.
- Есть регрессионные тесты изменённого поведения и проверки старого API с `access_token`.
- Для изменений обработки/развёртывания проверен реальный пайплайн в изолированном
  окружении; это не заменяется тестами с подменой конвертера или LMS.
- Изменения оценки сравниваются на эталонном корпусе, новые ограничения объяснены.
- Изменения данных имеют проверенную миграцию и способ восстановления. Резервная
  копия и повторный запуск не должны терять исходники, PDF и историю результата.
- Документация описывает выпущенное поведение; запланированные возможности остаются
  в роадмапе, а не объявляются доступными в README/API-справке.
- Версия меняется в `package.json`, производные метаданные синхронизируются стандартным
  процессом. Публикация и действия в GitHub выполняются только по отдельному запросу.
