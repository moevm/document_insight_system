# Критерии проверки документов

Справочник описывает текущую реализацию DIS: **39 ID для отчётов (`report`) и 23 для
презентаций (`pres`)**. Одинаковый ID может существовать у обоих типов. Ниже указаны
параметры конструкторов, способ вычисления оценки и ограничения каждой проверки.
Изменения поведения и порядок миграции — в [CHANGELOG](../CHANGELOG.md), запуск —
в [README](../README.md).

## Выбор набора

Сначала выберите тип документа и шаблон требований, затем состав критериев.
Базовый набор — пример конкретных требований, а не универсальный набор для любого файла.

| Задача | Тип и рекомендации |
|---|---|
| ВКР в Word | `report/VKR`; согласуйте стили, первые страницы и реквизиты с шаблоном. |
| Лабораторная работа | `report/LR`; по умолчанию основные заголовки — `heading 3`. |
| НИР или практика | `report/VKR` с явной картой НИР/практики и своим списком первых страниц. Одного `report_type` недостаточно. |
| SW в Markdown | `report/VKR`; используйте текстовые критерии и `sw_*`, исключите оформление Word и бланки ВКР. |
| Презентация | `pres`; учитывайте placeholders заголовков и нумерации PPTX. |

### Формат конфигурации

```json
{
  "name": "ExampleReport",
  "file_type": {"type": "report", "report_type": "VKR"},
  "min_score": 1.0,
  "raw_criterions": [
    ["simple_check"],
    ["literature_references", {"min_ref": 15, "max_ref": 100}],
    ["report_was_were_check", {"threshold": 3}]
  ]
}
```

Это структура набора, а не тело HTTP-запроса. Администратор сохраняет его через интерфейс;
поля маршрута создания описаны в README. Один элемент `raw_criterions` — `["id"]` или
`["id", {"параметр": "значение"}]`. Служебный `file_info` создаёт приложение; не передавайте
его в пользовательских параметрах.

Конструкторы принимают только параметры своих карточек. `null` в таблицах означает
Python `None`, JSON-массивы соответствуют спискам/кортежам. Обязательные параметры отмечены
отдельно. Значения по умолчанию конструктора могут отличаться от настроек базового набора.
`regex` у `template_name` включает текущий год **на момент импорта модуля**: в таблице
показано значение для 2026 года.

Неизвестный ID, неверная запись или ошибка конструктора создают видимую обязательную
ошибку с нулём. Эквивалентные записи дедуплицируются, включая `["id"]` и `["id", {}]`;
один ID с разными параметрами сохраняется несколько раз. Сохраняйте в наборах уникальные
записи: маршрут создания дополнительно сверяет их число после инициализации.

### Как получается оценка

Критерий возвращает `score` и `verdict`. Обычно оценка 0 или 1, иногда дробная.
Набор усредняет обычные оценки, округляет до трёх знаков и сравнивает с `min_score`.

| Режим | Влияние |
|---|---|
| Обычный | Входит в среднее. |
| Обязательный (`priority`) | Нулевая оценка обнуляет весь набор; ненулевая дробная оценка сама по себе этого не делает. |
| Рекомендация (`warning`) | Показывается в результате, исключается из среднего. |

`priority` и `warning` — свойства реализации, **не универсальные параметры** записи
в `raw_criterions`. Пустые правила у некоторых критериев включают рекомендательный режим;
это указано в карточках. Пустой набор или набор только из рекомендаций получает 0.
Исключение в `check()` заменяется результатом с нулём и сообщением для администратора;
его влияние определяется режимом критерия. Даже при провале обязательного критерия
оставшиеся проверки выполняются и видны в результате.

### Базовые наборы

[pack_config.py](../app/main/check_packs/pack_config.py) содержит `BaseReportCriterionPack`
(31 запись) и `BasePresentationCriterionPack` (24 записи), оба с `min_score=1.0`.
Это число записей, а не число уникальных ID: один критерий может вызываться с разными
параметрами. Например, презентационный набор несколько раз использует `find_slides`;
у `slide_every_task` и `conclusion_actual` задаёт `min_percent=70`, хотя конструкторы
по умолчанию используют 50. Не все зарегистрированные критерии входят в базовые наборы.

## Границы применимости

DOC/ODT предварительно конвертируются в DOCX, PPT/ODP — в PPTX. MD разбирается в заголовки,
абзацы, списки, таблицы и runs с жирностью; PDF генерируется через md2pdf. PDF не является
самостоятельным исходным форматом загрузки. Нумерация страниц в ссылках начинается с 1,
конец диапазона включительный.

Оформление Word и геометрия его страниц неприменимы к MD. Такие проверки обычно дают
отрицательный результат с пояснением, поэтому их нужно исключить из MD-набора.
Ряд отчётных проверок предварительно вызывает `has_enough_pages()`: для DOCX требуется
не меньше четырёх учитываемых страниц. Это не отдельное правило для всех критериев;
у MD этого предварительного ограничения нет, а требования к объёму задаёт `page_counter`.

Текст внутри картинок не распознаётся. Пагинация и переносы при конвертации влияют на
проверки PDF. LanguageTool и Git-ссылки требуют доступности внешнего сервиса/сети.
Лексическое сходство, «вода», аббревиатуры и геометрические приближения не доказывают
качество содержания; пороги следует проверить на представительных работах.

<a id="report-banned_words_check"></a>

### `banned_words_check` — Проверка наличия запретных слов в тексте отчёта

DOCX VKR/LR, MD. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/banned_words_check.py).

| Параметр | Значение по умолчанию |
|---|---|
| `headers_map` | `null` |

**Что проверяет.** Из выбранной карты берёт запретные/предупреждаемые слова и пороги. Морфологически нормализует строки PDF и считает все вхождения слов/словосочетаний.

**Результат.** 1 при count ≤ min_count; 0.5 при min_count < count ≤ max_count; иначе 0.

**Настройка и ограничения.** Предупреждаемые слова выводятся отдельно и не влияют на балл. Сканируется весь PDF. Карта выбирается headers_map либо VKR_HEADERS/LR_HEADERS; отсутствующие пороги заменяются 3/6.

<a id="report-banned_words_in_literature"></a>

### `banned_words_in_literature` — Проверка наличия запрещенных слов в списке литературы

DOCX VKR/LR, MD. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/banned_words_in_literature.py).

| Параметр | Значение по умолчанию |
|---|---|
| `banned_words` | `null` |

**Что проверяет.** В абзацах раздела источников ищет заданные строки/домены с границами слова, без учёта регистра.

**Результат.** 0 при любом совпадении; иначе 1. Отсутствующий/пустой список источников не проходит.

**Настройка и ограничения.** banned_words добавляет слова к встроенным habr, medium, stackoverflow, sky.pro, geeksforgeeks, wikipedia; список класса не изменяется. Качество и достоверность остальных источников не оцениваются.

<a id="report-compare_goal_and_content_check"></a>

### `compare_goal_and_content_check` — Проверка соответствия цели и содержания

DOCX/MD с введением и основным текстом. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/compare_goal_and_content.py).

| Параметр | Значение по умолчанию |
|---|---|
| `min_similarity` | `0.1` |

**Что проверяет.** Выделяет цель из введения; вычисляет TF-IDF-сходство её n-грамм с текстами разделов без введения, литературы и приложения. Проверяет среднее абсолютное сходство.

**Результат.** 1 при среднем ≥ min_similarity, иначе 0; отсутствующая цель или основной текст не проходят.

**Настройка и ограничения.** Сходство 0–1 — лексическая метрика, не доказательство раскрытия цели. Выделение цели зависит от формулировки и границ предложения.

<a id="report-compare_tasks_and_content_check"></a>

### `compare_tasks_and_content_check` — Проверка соответствия задач и содержания

DOCX/MD с введением и основным текстом. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/compare_tasks_and_content.py).

| Параметр | Значение по умолчанию |
|---|---|
| `min_similarity` | `0.15` |
| `specific_min_similarity` | `0.05` |
| `min_tasks` | `3` |

**Что проверяет.** Выделяет задачи после маркера задач до объекта/предмета исследования. Сравнивает объединённые задачи и каждую отдельно с разделами по TF-IDF n-граммам.

**Результат.** Нужны ≥ min_tasks; среднее всего списка ≥ min_similarity и каждого пункта ≥ specific_min_similarity. Иначе 0, при выполнении 1.

**Настройка и ограничения.** Количество — число выделенных пунктов. Введение исключено из сравнения. Проценты лексического сходства нельзя интерпретировать как долю фактически выполненной работы.

<a id="report-decimal_places_check"></a>

### `decimal_places_check` — Проверка на избыточное количество десятичных знаков

DOCX VKR/LR, MD. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/decimal_places.py).

| Параметр | Значение по умолчанию |
|---|---|
| `max_decimal_places` | `2` |
| `max_violations` | `3` |

**Что проверяет.** В PDF до списка источников находит числа с точкой/запятой и считает знаки в дробной части. Отсеивает многокомпонентные даты/IP/нумерацию и сгруппированные целые.

**Результат.** 0, если нарушений > max_violations; иначе 1, но найденные нарушения выводятся.

**Настройка и ограничения.** Число 1234.5678 распознаётся. Неоднозначность десятичного разделителя и разделителя тысяч остаётся; это не математический разбор формул.

<a id="report-empty_task_page_check"></a>

### `empty_task_page_check` — Проверка заполнения страницы с заданием

PDF-структура задания VKR, обычно DOCX. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/empty_task_page_check.py).

Пользовательских параметров нет.

**Что проверяет.** На второй странице ищет заголовок задания, заполненные значения Студент/Группа/Руководитель/Тема работы и минимум две даты.

**Результат.** 1 при заполненных полях, иначе 0.

**Настройка и ограничения.** Жёсткая привязка к второй странице и русским меткам ВКР; не применять к SW или иному бланку без таких полей. Проверяет наличие содержимого, а не правильность ФИО и дат.

<a id="report-first_pages_check"></a>

### `first_pages_check` — Проверка наличия обязательных страниц в отчете

DOCX: по умолчанию VKR; LR/другие шаблоны с headers. Режим: **обязательный**. [Реализация](../app/main/checks/report_checks/first_pages_check.py).

| Параметр | Значение по умолчанию |
|---|---|
| `headers` | `null` |

**Что проверяет.** Ищет первые страницы в заданном порядке по первой строке PDF. По умолчанию: титул, задание ВКР, календарный план, Реферат, Abstract, Содержание.

**Результат.** 1, если найдены все обязательные страницы в порядке, иначе 0.

**Настройка и ограничения.** headers задаёт упорядоченный список названий. MD не имеет make_headers и получает сообщение о неприменимости; LR без headers не проходит. Первая строка и оформление PDF влияют на распознавание.

<a id="report-header_check"></a>

### `header_check` — Проверка оформления заголовков отчета

DOCX VKR/LR; НИР/практика через headers_map. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/chapters.py).

| Параметр | Значение по умолчанию |
|---|---|
| `headers_map` | `null` |

**Что проверяет.** Сопоставляет заголовки с docx_style и regex выбранной карты; сравнивает эффективные свойства каждого run с заданным шаблоном.

**Результат.** 1 при отсутствии ошибок текста/стиля, иначе 0.

**Настройка и ограничения.** headers_map=null выбирает VKR_HEADERS или LR_HEADERS. Пользовательская карта выбирается по имени из CONFIGS. MD не поддерживается; имя report_type не выбирает автоматически карту НИР.

<a id="report-headers_at_page_top_check"></a>

### `headers_at_page_top_check` — Проверка расположения разделов второго уровня с новой страницы

DOCX VKR/LR. Режим: **обычный**. [Реализация](../app/main/checks/report_checks/headers_at_page_top_check.py).

| Параметр | Значение по умолчанию |
|---|---|
| `headers` | `null` |

**Что проверяет.** В VKR берёт heading 2 до приложения и сопоставляет с первыми строками PDF; в LR ищет явно переданные headers в начале страниц после титула.

**Результат.** 1, если все требуемые заголовки распознаны в начале страниц, иначе 0.

**Настройка и ограничения.** В VKR headers заменяется списком распознанных заголовков. В LR непустой headers обязателен. Для MD проверка неприменима; переносы строк и номера в PDF могут мешать распознаванию.

<a id="report-headers_references_check"></a>

**Что проверяет.** Берёт ближайший текстовый блок к каждому рисунку как предполагаемую подпись. На слайдах с другим содержимым требует слово «Рисунок» без учёта регистра; для слайдов только с рисунками подпись необязательна.

**Результат.** 1 при отсутствии нарушений, иначе 0.

**Настройка и ограничения.** Выбор подписи зависит от геометрии блоков и может ошибиться при сложной компоновке. Число/формат номера рисунка не проверяются.

### `pres_image_share` — Проверка доли объема презентации, приходящейся на изображения

**Настройка и ограничения.** Измеряет долю слайдов с картинками, не площадь изображения и не объём файла. Таблицы отдельно не считаются изображениями.

### `pres_was_were_check` — Проверка на пассивные конструкции, начинающиеся с Был/Была/Было/Были, которые можно убрать без потери смысла

<a id="pres-slide_every_task"></a>

### `slide_every_task` — Наличие слайдов, посвященных задачам

|---|---|
| `min_percent` | `50` |

**Настройка и ограничения.** Номер, набранный обычным текстовым блоком, не является placeholder и может не распознаваться.

<a id="pres-slides_headers"></a>

**Настройка и ограничения.** Автоматический визуальный перенос из-за ширины блока не измеряется. Произвольный текстовый блок вместо заголовка не заменяет placeholder.

### `template_name` — Проверка соответствия названия файла шаблону

<a id="pres-theme_in_pres_check"></a>

### `theme_in_pres_check` — Проверка упоминания темы в заголовках презентации

**Результат.** min(процент/limit, 1); отсутствие темы/слайдов даёт 0.

**Настройка и ограничения.** limit в диапазоне (0,100]. skip_slides_nums — номера от 1; skip_slides_titles — фрагменты названий без учёта регистра. Тело слайда не участвует.

### `verify_git_link` — Проверка действительности ссылок на репозитории

## Карты заголовков

Карты находятся в [StyleCheckSettings.CONFIGS](../app/main/checks/report_checks/style_check_settings.py).
Передавайте имя карты в `headers_map` тем критериям, которые принимают этот параметр.
Не все элементы CONFIGS являются картами заголовков: там есть также конфигурации стилей.

| Имя | Назначение |
|---|---|
| `VKR_HEADERS` | Структура ВКР, заголовки основных разделов `heading 2`. |

### Компоненты раздела

[SECTION_CONFIG](../app/main/checks/report_checks/section_component_config.py) задаёт
компоненты `report_section_component`. Для `chapter="Введение"` и `patterns=null` это
актуальность, объект исследования, предмет исследования, цель работы, задачи и практическая
значимость. Актуальность по умолчанию освобождена от проверки жирности. Для остальных
разделов стандартные компоненты — цель/задачи, исключений жирности нет.
Явные `patterns` и `bold_check_exceptions` заменяют соответствующие списки, а
`check_bold=false` выключает только проверку начертания.

## Конфигурации SW

Три критерия принимают `sections_info` как имя встроенной конфигурации или собственный
JSON-объект. Имена одинаковы, но **каждый критерий содержит свой словарь**:
`SW_KEY_QUESTIONS_SECTIONS`, `SW_ANALOGS_SECTIONS`, `SW_FINAL_SECTIONS`.
`null` выбирает первый, неизвестное имя вызывает ошибку конструктора, `{}` включает
рекомендательный режим. Названия разделов сравниваются точно, с учётом регистра.

### `sw_sections_size_check`

`words` и `sentences` — верхние пределы непосредственного текста раздела.
Предложения здесь считаются разделением по точке, слова — по пробелам.
Пустой существующий раздел проходит верхний предел; подразделы не суммируются.

```json
{
  "SW_KEY_QUESTIONS_SECTIONS": {
    "Проблема": {
      "words": 15,
      "sentences": 1
    },
    "Объект исследования": {
      "words": 15,
      "sentences": 1
    },
    "Предмет исследования": {
      "words": 15,
      "sentences": 1
    },
    "Цель дипломного исследования": {
      "words": 30,
      "sentences": 1
    },
    "Цель на текущий семестр": {
      "words": 30,
      "sentences": 1
    }
  },
  "SW_ANALOGS_SECTIONS": {},
  "SW_FINAL_SECTIONS": {}
}
```

### `sw_section_lit_reference`

`count` — минимум уникальных номеров источников во всём разделе с потомками.
`subchapters` — минимум для каждого непосредственного подраздела с его потомками.
Если подразделов нет, этот параметр не требует их создать. Проверку самой библиографии
выполняет отдельный `literature_references`.

```json
{
  "SW_KEY_QUESTIONS_SECTIONS": {
    "Актуальность": {

    }
  },
  "SW_ANALOGS_SECTIONS": {
```

Технический тип пака — `{"type":"report","report_type":"VKR"}`.
Ниже показаны фрагменты raw_criterions; состав полного пака определяется требованиями задания.
Проверки текста, ссылки на рисунки/таблицы и литературу можно сочетать с SW-правилами.

### Ключевые вопросы

```json
[
  ["simple_check"],
  ["needed_headers_check", {"headers_map":"OPNP_HEADERS"}],
  ["sw_sections_size_check", {"sections_info":"SW_KEY_QUESTIONS_SECTIONS"}],
  ["sw_section_lit_reference", {"sections_info":"SW_KEY_QUESTIONS_SECTIONS"}],
  ["sw_tasks_check", {"min_tasks":3,"max_tasks":5}]
]
```

h1 должен быть «Ответы на ключевые вопросы», а заголовки разделов — h2.
Задачи размещаются в отдельном разделе «Задачи», каждый пункт отдельным элементом списка.

### Сравнение аналогов — задание 2

```json
[
  ["needed_headers_check", {"headers_map":"OPNP_HEADERS"}],
  ["report_section_component", {
    "chapter":"Принцип отбора аналогов",
    "patterns":["запрос","поиск"],
    "check_bold":false
  }],
  ["sw_section_banned_word", {"sections_info":"SW_ANALOGS_SECTIONS"}],
  ["sw_section_lit_reference", {"sections_info":"SW_ANALOGS_SECTIONS"}],
  ["literature_references", {"headers_map":"OPNP_HEADERS"}],
  ["report_was_were_check", {"threshold":3}],
  ["spelling_check"]
]
```

h1 — «Сравнение аналогов». В этом примере компоненты проверяются только на наличие;
если жирное начертание является требованием, задайте `check_bold=true` или уберите этот параметр.
Карты размера SW_ANALOGS_SECTIONS сейчас пусты: для ограничений размера нужен собственный словарь.

### Итоговый материал — задание 3

```json
[
  ["needed_headers_check", {"headers_map":"OPNP_HEADERS"}],
  ["report_section_component", {
    "chapter":"Введение",
    "patterns":["цель","задачи","объект","предмет"]
  }],
  ["sw_keywords_check", {"min_key_words":3}],
  ["sw_section_banned_word", {"sections_info":"SW_FINAL_SECTIONS"}],
  ["sw_section_lit_reference", {"sections_info":"SW_FINAL_SECTIONS"}],
  ["literature_references", {"headers_map":"OPNP_HEADERS","min_ref":5}],
  ["banned_words_in_literature"],
  ["report_was_were_check", {"threshold":3}],
  ["spelling_check"]
]
```

После h1 должен идти абзац «Ключевые слова: ...», затем разделы.
При заголовке h1, отличном от первых двух специальных названий OPNP, выбирается any_header.
В этом примере компоненты введения должны быть выделены жирным.
`sw_tasks_check` добавляйте, только если предусмотрен отдельный раздел «Задачи».
Лимиты коротких разделов и «воды» согласуйте с объёмом задания; универсальные минимумы могут оказаться избыточными.

### Минимальная структура Markdown

```markdown
# Ответы на ключевые вопросы

## Проблема
Краткая формулировка проблемы.

## Актуальность
Обоснование со ссылкой на источник [1].

## Задачи
- Первая задача.
- Вторая задача.
- Третья задача.

## Список использованных источников
1. Описание источника.
```

Фрагмент показывает уровни заголовков и отдельные элементы списка задач. Он не проходит
полную `OPNP_HEADERS`: остальные обязательные разделы нужно добавить по таблице карты.
Не помещайте вводный абзац между заголовком «Задачи» и списком, если не хотите учитывать
его как отдельный блок в `sw_tasks_check`.

## Проверка настроенного набора

1. Сверьте ID с типом документа и параметры с карточкой.
2. Выберите подходящую карту и точное название h1 для MD; проверьте уровни заголовков.
3. Проверьте значения порогов, единицы измерения и пустые правила.
4. Запустите набор на правильном документе и на документе с ожидаемым нарушением.
5. Отличайте отрицательную оценку от внутренней ошибки критерия; смотрите журнал и PDF.

Регрессионные сценарии находятся в [tests/criteria](../tests/criteria) и
[tests/reports](../tests/reports). Команды и границы тестирования — в
[README](../README.md#разработка-и-проверки). Тесты внешних границ используют подмены;
реальная пагинация, доступность LanguageTool и репозиториев требуют отдельной проверки.
